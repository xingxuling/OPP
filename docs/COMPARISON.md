# OPP 和常见接口方案的关系

OPP 不是用来替代 REST、gRPC、SDK、OpenAPI、MCP 或 A2A 的。它更像一层“接口理解和桥接检查”：先把双方的能力、输入输出和约束看清楚，再判断是否兼容、是否需要转换，以及这次执行如何留下可验证记录。

| 技术/方式 | 它主要解决什么 | OPP 补在哪里 |
|---|---|---|
| **直接写 Adapter** | 针对两个具体系统手工写转换代码 | OPP 适合在接入对象越来越多时，先自动检查接口差异，再决定是否生成受限桥接 |
| **SDK / REST / gRPC** | 已知接口怎么调用 | OPP 不替代调用方式；它关注两个端点是否真的兼容 |
| **OpenAPI / JSON Schema** | 描述接口和数据结构 | OPP 可以读取结构信息并参与兼容性判断，但不等于 OpenAPI 替代品 |
| **MCP** | Agent 如何发现和调用工具 | OPP 可以放在工具接入前后做能力、输入输出和桥接检查 |
| **A2A** | Agent 与 Agent 如何协作通信 | OPP 更关注能力契约、数据形状和互操作关系 |
| **TINP** | 身份、权限、路由、恢复和执行证据 | OPP 先回答“能不能接”；TINP 再处理“谁能调用、失败怎么办” |

## 为什么不直接写几十行 Adapter？

如果只有两个稳定系统，直接写 Adapter 往往更简单。

OPP 开始有价值的情况是：

- 接入对象越来越多；
- API / Schema 经常变化；
- Agent 会动态发现新工具；
- 想在真正执行之前先判断兼容性；
- 需要区分“精确兼容、可转换、有损、不兼容、未知”；
- 需要保留桥接和执行对应的回执。

也就是说，OPP 不是为了让简单集成变复杂，而是为了让**不断重复出现的集成判断**变得更可检查、更可复用。

## 一句话区分

```text
API / SDK / MCP / A2A：怎么调用
OPP：两个端点到底能不能接、需要怎么转
TINP：谁能调用、怎么传、失败后怎么恢复
```

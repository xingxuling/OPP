# OPP 试点指标

这份文档不预设“OPP 能节省多少时间”之类的营销数字。目标是把真实试点中的收益和不足量出来，再决定哪些能力值得产品化。

## 为什么要量

OPP 当前是 Candidate。它已经能做接口扫描、兼容性判断、受限桥接和具体链路互操作，但这还不能自动推出商业 ROI。

真正有意义的问题是：

- 和纯手工 Adapter 相比，第一次接入到底快了多少；
- Schema 变化后，问题能不能更早被发现；
- 哪些差异能自动桥接，哪些仍然要人工判断；
- 出错后，能不能更快知道失败在哪里；
- 一次真实集成需要多少人工介入。

## 建议记录的指标

| 指标 | 手工基线怎么测 | OPP 怎么测 |
|---|---|---|
| 首次接入耗时 | 从读文档到第一个可运行 Adapter | 从扫描开始到第一个 PASS 或明确 FAIL |
| 接口理解时间 | 人工识别输入、输出和字段差异 | OPP 静态提取 + 人工复核 |
| Schema 漂移发现时间 | 变化发生到人工发现 | 重新扫描到产生差异报告 |
| 可自动桥接比例 | 不适用 | 测试接口中可生成受限 bridge 的比例 |
| 人工介入次数 | 编写/修改 Adapter 的次数 | 补充语义、确认 lossy、修改 plan 的次数 |
| 失败可解释率 | 失败是否能定位原因 | 是否能给出 incompatible / unknown / execution failure 等明确原因 |
| 回执覆盖率 | 是否有完整执行记录 | 完成执行的链路是否都有 receipt |
| 维护工作量 | 接口变化后修复代码量和时间 | 重新扫描、更新 bridge、重新验证的工作量 |

## 第一阶段试点建议

优先找 3–5 组彼此独立的真实项目，而不是继续只测仓库内 fixture：

1. 一个 Python API / SDK 与另一个 Python 服务；
2. 一个 TypeScript 项目与 JSON Schema / OpenAPI 描述的服务；
3. 一个 Agent 工具 / MCP Server 与现有业务服务；
4. 一个旧 API -> 新 API 的迁移场景；
5. 一个明确存在字段重命名、默认值和多余字段的企业内部接口。

第一阶段目标不是证明“OPP 比所有方案更快”，而是找出：**在哪些集成类型里它确实省事，在哪些类型里还不值得用。**

## 对外表达规则

在没有足够真实样本前，不写：

- “节省 70% 开发时间”；
- “降低 90% 集成成本”；
- “零人工接入”；
- “任意 API 自动兼容”。

有真实试点后，只报告实际样本、测试条件和结果，不把局部结果外推成普遍结论。

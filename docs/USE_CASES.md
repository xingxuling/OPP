# OPP 使用场景

这份文档只回答一个问题：**什么时候值得用 OPP？**

OPP 不是用来替代 HTTP、REST、MCP、A2A 或现有 SDK 的。它更适合放在这些接口之上，负责看懂能力、比较接口、生成受限转换，并留下验证结果。

## 1. 两个项目能不能直接接

你有一个生产端和一个消费端：

```text
Project A -> ? -> Project B
```

A 会输出数据，B 也有清楚的输入要求，但字段名、结构或类型不完全一致。

OPP 可以先静态扫描双方接口，再给出兼容性判断：

```text
exact        精确兼容
structural   结构兼容
lossy        可以转换，但会丢信息
incompatible 不兼容
unknown      证据不足，不能判断
```

如果转换只需要 OPP 当前允许的声明式操作，工具链可以进一步生成桥接计划。

适合：

- 两个内部服务第一次对接；
- 旧 API 迁移到新 API；
- 代码仓库合并前做接口审计；
- 判断一个开源项目能不能复用进现有系统。

## 2. 给 AI Agent 接工具

AI Agent 经常能找到“一个工具”，但真正接入时还会遇到：

- 输入字段不一样；
- 输出结构不一样；
- 同名能力实际契约不同；
- 缺少可以复核的执行记录。

OPP 可以把工具能力描述、输入输出和证据放进统一结构，再检查两个端点是否真的匹配。

一个典型流程是：

```text
Agent
  -> capability description
  -> compatibility check
  -> bridge plan
  -> tool invocation
  -> receipt
```

当前实现适合做原型、集成审计和受控调用实验。它不等于一个已经完成生产安全认证的 Agent 网关。

## 3. 自动生成“胶水代码”之前先做结构判断

很多集成项目的问题不是代码写不出来，而是太早开始写。

传统流程常常是：

```text
读文档 -> 猜字段 -> 写 adapter -> 跑一下 -> 再改
```

OPP 更适合先做：

```text
扫描 -> 提取接口 -> 比较 -> 生成桥接计划 -> 再决定是否执行
```

这样能把“哪些地方是确定的、哪些地方会丢信息、哪些地方根本不知道”提前暴露出来。

## 4. 需要留下证据的自动化

如果一次自动化不仅要“跑完”，还要回答：

- 当时双方声明的能力是什么；
- 使用了什么转换；
- 实际调用了哪个函数；
- 结果是否通过验证；
- 这次执行对应哪份回执；

那么 OPP 的 evidence / receipt 结构会比只保存日志更合适。

## 什么时候不该用

如果两个系统已经有稳定 SDK，字段完全一致，而且没有能力协商、审计或桥接需求，直接调用现有 SDK 通常更简单。

如果你需要的是生产级身份、权限、路由、断线恢复和节点切换，OPP 也不是完整答案。这部分更接近 TINP 的职责范围。

## 当前边界

OPP 目前是 Candidate：

- 已有真实的受控互操作执行；
- 当前原生调用适配器主要面向 Python 顶层函数；
- 不声称任意第三方项目都能自动连接；
- 不声称具备强 OS 级沙箱；
- 不声称已经成为外部标准。
